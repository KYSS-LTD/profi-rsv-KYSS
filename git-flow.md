# 🌳 Git Flow
Для хакатона используется адаптированный Git Flow, оптимизированный под короткий цикл разработки.

Такой подход выбран осознанно, потому что срок разработки ограничен примерно 4 днями, а команда состоит из небольшого количества участников. В таких условиях классический Git Flow с большим количеством согласований, обязательным code review и длинной цепочкой интеграции будет избыточен.

Для хакатонного формата важнее быстро доставлять рабочие инкременты, при этом сохраняя контроль над стабильностью общей кодовой базы.

Поэтому используется схема с персональными ветками <span style="color:red;">develop-*</span>:

<span style="background-color:palegreen;">Пример — develop-ivan, develop-danila, develop-artem</span>

Каждый участник ведёт разработку в своей персональной ветке, изолируя незавершённые изменения от общей интеграционной ветки <span style="color:red;">develop</span>. Это снижает риск поломки общей ветки, упрощает локализацию проблем и позволяет участникам команды двигаться параллельно без постоянной блокировки друг друга.

Если задача крупная, рискованная или требует отдельной проверки, от персональной ветки может создаваться отдельная <span style="color:red;">feature/*</span>-ветка.

Для небольших задач допускается разработка напрямую в персональной <span style="color:red;">develop-*</span>-ветке, чтобы не создавать лишнюю операционную нагрузку.

Примеры веток:

<span style="color:red;">main</span> — стабильная релизная ветка. <span style="background-color:palegreen;">Пример — main</span>

<span style="color:red;">develop</span> — общая интеграционная ветка разработки. <span style="background-color:palegreen;">Пример — develop</span>

<span style="color:red;">develop-*</span> — персональная ветка разработки участника команды. <span style="background-color:palegreen;">Пример — develop-ivan, develop-danila, develop-artem</span>

<span style="color:red;">feature/*</span> — отдельная ветка под новую функциональность или крупную задачу.
Наименование ветки должно соответствовать регулярному выражению:

<span style="background-color:gainsboro;">^feature/KM-\d+-[\w-]+$</span>

<span style="background-color:palegreen;">Пример — feature/KM-5150-login-endpoint</span>

<span style="color:red;">bugfix/*</span> — исправление некритичных багов.
Наименование ветки должно соответствовать регулярному выражению:

<span style="background-color:gainsboro;">^bugfix/KM-\d+-[\w-]+$</span>

<span style="background-color:palegreen;">Пример — bugfix/KM-5151-fix-auth-validation</span>

<span style="color:red;">hotfix/*</span> — срочная правка, которая может создаваться от <span style="color:red;">main</span>.
Наименование ветки должно соответствовать регулярному выражению:

<span style="background-color:gainsboro;">^hotfix/KM-\d+-[\w-]+$</span>

<span style="background-color:palegreen;">Пример — hotfix/KM-5152-fix-production-crash</span>

Общая ветка <span style="color:red;">develop</span> используется как интеграционная точка, куда попадают только проверенные и рабочие изменения из персональных веток.

Перед финальной демонстрацией стабильное состояние из <span style="color:red;">develop</span> вливается в <span style="color:red;">main</span>.

Обязательные формальные апрувы не вводятся, потому что при небольшом составе команды и ограниченном времени это создаст лишнюю бюрократию. Вместо этого применяется lightweight-подход: разработчик самостоятельно проверяет сборку, запуск и базовую работоспособность своей части перед интеграцией. Для рискованных изменений проводится быстрая синхронизация с командой перед merge в develop.

Такой процесс позволяет сохранить баланс между скоростью разработки и контролем качества: команда быстро двигается к MVP, но при этом не превращает общую ветку в хаотичное место для незавершённых изменений.
